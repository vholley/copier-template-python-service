# How work flows here

Two directories hold text. `docs/` is reference material generated by the
template, not tracked by git, restored with `uv run python scripts/task.py restore`.
`working/` (this directory) is tracked and holds everything the process reads
and writes: the living spec, decisions, constraints, standards, and history.
Nothing the process depends on lives in `docs/`.

You need to remember three commands. Everything else is shown to you when it
applies.

    make start     asks what you are here to do
    make status    where am I, what is blocking, what is next
    make help      every command, grouped by when it applies

The diagram of the whole flow is `docs/workflow.mermaid`.

## Starting work {#start}

`make start` looks at your branch and asks one question with the answers that
apply. Typical answers:

| Answer | What happens | What you will owe |
|---|---|---|
| A small fix with no change in behavior | a branch, no work item | a PR with a one-line description |
| Something the software will do differently | a work item on a branch | sign an intent, a spec, and the tests |
| Something broken that should work | a work item, bug-fix path | sign an intent and a diagnosis |
| Not sure yet | an exploration branch that never merges | nothing, until you know |
| Don't want this process for this work | see [opting out](#opt-out) | one signature |

`make start TICKET=<key>` uses your ticket key as the work-item id and branch
name. Claude Code runs `/start` for you when you describe a task, so you rarely
type it.

## The stages {#stages}

For a change: intent → clarify → spec → plan → red → implement → verify → review.
For a bug: intent → diagnose → plan → implement → verify → review.

Each stage has a slash command (`/intent`, `/clarify`, `/spec`, `/plan`,
`/red`, `/implement`, `/diagnose`) that the agent runs. Three of them end with
you signing: intent, spec, red (or intent and diagnosis for a bug). The agent
cannot write code until the spec (or diagnosis) is signed, and cannot end a
turn until `make green` passes.

## Signing {#signing}

An acceptance is a git commit signed with your SSH key. The agent prepares it;
you sign it in your own shell:

    make accept STAGE=intent      # also: spec, red, diagnosis, decisions, opt-out

Your SSH key must be registered on GitHub as a signing key and protected per
use: either a passphrase-protected key that is not loaded into ssh-agent, or an
agent that prompts on each use (1Password, or `ssh-add -c`). CI verifies the
signature on acceptance commits only. Nothing else you commit needs signing.

## Green {#green}

`make green` autofixes, then runs lint, types, tests for the members you
touched, the constraints, budgets, and spec coverage. The session's stop hook
requires it to have passed since your last edit. Three blocks in a row and the
item is [escalated](#escalated).

## Checks and constraints {#checks}

`make ci` is what CI runs. `working/architecture/constraints.md` lists the
project's invariants; each names the check that enforces it (`ruff`,
`importlinter`, or `scripts/delivery/constraints.py`). No invariant is active
unless it is listed there. {#constraints}

`working/standards/budgets.md` holds every numeric limit (diff size, file
length, coverage of changed lines, review sizes). A dimension with no budget is
not optimized, by decision. {#budgets}

## Tests {#tests}

Tests come first: each criterion gets a failing test before any implementation,
and CI checks the order. Tests carry `@pytest.mark.spec("<file>.md#<anchor>")`
naming the living-spec statement they prove. The ratchet refuses deleted or
weakened assertions without the `test-change-approved` label. {#red-first}

The living spec, one file per member under `working/spec/`, describes what the
system does; every statement has a test, and a change to behavior updates it in
the same PR. {#living-spec}

## The spec {#spec}

`/spec` writes `spec.md` and `criteria.json`. Each criterion has a class
(`working/standards/criteria-templates.md` says which classes a change needs),
a verify command, and starts as failing. It passes only with evidence.

## Bugs {#diagnosis}

`/diagnose` writes `diagnosis.md`: a reproduction, evidence you can open, and a
cause claim tagged observed, inferred, or hypothesized. Source edits are blocked
until the cause is `confirmed`, and CI checks that the fix lands where the
diagnosis says.

## Review and the contract {#review}

A pull request carries the whole chain. `make contract` runs the same checks CI
will: signed acceptances, nothing edited after signing, tests before code,
every decision with a consequence and a sign-off, the living spec updated, the
diff within budget, the PR description complete. {#contract}

The reviewer answers three questions: did the spec solve the intent, were the
decisions sound, is there anything the spec did not require. One approval from
someone other than the author is all that is ever required.

## When a quick change turns out not to be one {#bounced}

If CI classifies your PR as a behavior change and there is no work item, it
tells you: `make start` (choose "add or change behavior"), then
`make adopt-branch TICKET=<key>` to attach the branch. Your code stays; the
tests-before-code check is waived for bounced items.

## When the agent is stuck {#escalated}

After three blocked attempts the item is escalated and `make status` lists the
three ways forward: back to implementation (after you fix the criterion or make
the decision), back to spec, or `make abandon`.

## State {#state}

`.work/<id>/state.json` is a cache of what git and the files already say. If it
is ever wrong or missing: `make rebuild ID=<id>`. `make status` names the repair
whenever something disagrees.

## Protected paths {#protected}

The agent cannot edit `working/architecture/`, `working/standards/`,
`.claude/`, `scripts/`, or `.github/` in a session. Change them in a pull
request. Tests and the living spec are not blocked; the ratchet and review
protect those.

## Deployable surface {#deploy}

Nothing from the process reaches a container: `.dockerignore` and
`make deploy-surface` enforce it.

## The evaluator {#evaluator}

A separate read-only agent grades each criterion against its evidence and
writes `evaluator-report.md`. It cannot change anything.

## Observations {#observations}

Something wrong that no written rule covers is an observation, recorded with
`make observe` and a concrete consequence. Hypothesized consequences are not
recorded; observed ones are bugs (`make start`); inferred ones expire at the
next weekly audit unless they become work.

## The issue log {#log}

`working/log.md` is the running record of what went wrong and what definition
was missing: `make log WHAT="..." MISSING="..." [FIX="..."]`. Entries close
once. The weekly audit lists the open ones. Read it before writing a rule: the
failure it addresses is probably already there.

## Decisions {#decisions}

Every decision the agent makes is written in `.work/<id>/decisions.md` with what
was considered instead and what happens if it is wrong. You accept them when you
sign the spec. None are made silently.

## Opting out {#opt-out}

    make opt-out                      # optional: REASON="..."
    make accept STAGE=opt-out         # in your shell

After that, no stage guards or prompts on this branch. What still applies
because it belongs to the repository: `make ci`, the test ratchet, the
protected-path block, and one reviewer's approval. To rejoin: `make start`.

## Session hooks {#hooks}

Claude Code hooks (`.claude/settings.json`, `scripts/hooks/`) enforce the
above in a session. Every block says what was refused, why, the exact next
command, and links here.

## Skills {#skills}

The stage commands live in `.claude/`. `deslop` is vendored from the team's
skill; `.claude/VENDORED.md` records its source and digest.

## Commands

Generated from `working/commands.toml`; `make help` prints the current list.
